# 基于现有示例开发任务

排查环境、Controller、provider或renderer时遵循[诊断与代码边界规范](../../docs/global/diagnostics-and-code-boundaries.md)：通过现有接口、外部包装、诊断子类／小范围重写或局部fixture观察和干预，不向正常核心路径增加实验名、测试判断或probe开关。方法说明与可复用诊断入口放`task_env/diagnostics/<topic>/`，本次临时输出放ignored workspace；正式修复仍归各自产品owner。既存耦合按版本收尾计划处理，不要求开发新任务前全面解耦。

先阅读[安装与启动](../../docs/module/task_env/v2.1.1/guides/installation-and-start.md)，准备与本 Core 匹配的解释器、GeoPhys 源码和资产。先完成单环境闭环；训练、并行和渲染不是前提。单环境生命周期源码和无引擎契约已获[有限接收](../../docs/module/task_env/v2.1.1/maintenance/reviews/20261105_lifecycle_unification_sol_review.md)，后续维护仍待复审；本文不把内部 adapter 宣称为稳定扩展 API。

## 阅读和修改声明式示例

[`examples/tasks/declared_marker.py`](../../examples/tasks/declared_marker.py) 在模块导入时用 `@register_env()` 注册 `MarkerHeightEnv`。其 `declaration()` 返回 `PandaBoxDeclaration`：声明 task/artifact/object identity、Panda/table/box 组合、物理 timebase、reset 的 XY 范围和 `SemanticDefinition`。`evaluate_task(state, semantics)` 读取公开状态，返回 `task_env.environment.TaskEvaluation(reward, success, failure, metrics, reward_terms)`。它没有 Task-owned Solution；不要对它调用 `prepare_expert()` 或 `step_expert()`。

复制示例到自己的模块并更换唯一 UID，保持 class `uid` 与 declaration 的 `task_id` 一致；调整 object identity、资产组合、reset 和评价时一起检查引用、单位和任务成功定义。示例的 `selected_binding` 显式选择现有世界坐标 pose 动作契约与 selected 观测契约，提供编译器、reset、评价及机器人 scalar 控制绑定；这些经现有 `ReferenceTaskBinding` 接入。其无 provider 编译入口负责公共构造接线，公共 factory 使用规范 Env 的共同 resolved-config 组装。Controller 编译和来源摘要由 assembly 完成。 来源记录识别普通函数、可调用对象和 `functools.partial` 的实现文件；它不自动追踪闭包或 partial 参数里的间接依赖。该接线仍是内部实现，适用于已存在的 Panda/table/box 路线，不能据此推断任意资产、动作或 provider 可用。一般任务组合与 `TaskDefinition` 的职责见 [TaskDefinition](api/semantics/task_definition.md) 和[资产指南](资产导入与二次开发指南.md)。

导入示例模块注册任务后可经 public factory 检查。以下流程在源码 `bc190964`、已有 MuJoCo 3.8.1 CPU 环境中完成过一次有界 reset／采样动作／step／close；检查中额外固定了 action-space seed。结果和来源见[维护记录](../../docs/module/task_env/v2.1.1/maintenance/reviews/20261105_pre_stage3_continuation.md)。这不证明任务成功、全新安装或其他 provider 可用：

```python
import examples.tasks.declared_marker  # 注册示例任务
from task_env import make_env

env = make_env("marker-height-example-v1", config={
    "execution": {"physics_provider": "mujoco", "physics_backend": "cpu"},
    "episode": {"horizon": 10},
})
try:
    observation, info = env.reset(seed=31)
    assert env.observation_space.contains(observation)
    action = env.action_space.sample()
    observation, reward, terminated, truncated, info = env.step(action)
    assert env.observation_space.contains(observation)
finally:
    env.close()
```

运行前须准备所选 provider 及 menagerie 资产；示例注册和导入本身不证明 provider 可运行。selected 当前只接受 state-only；未知配置、冲突 alias 和不支持的 provider/backend/render 会失败。动作和 observation 的 shape、dtype 与边界以该环境实际的 spaces 和 metadata 为准；Panda 的 8 维输入不适用于 Pendulum 或 TwoWheel。

## 从示例定位需要修改的内容

| 要开发的内容 | 现有位置 | 修改时需要核对 |
| --- | --- | --- |
| 注册与 UID | `MarkerHeightEnv` 的 `@register_env()` 和 `uid` | 模块导入后注册；`uid` 与 declaration 的 `task_id` 相同，再用 `make_env(uid, config=...)` 创建 |
| 资产与任务声明 | `declaration()` 中的 `PandaBoxDeclaration`、`SemanticDefinition` 和 `Timebase` | 选择已有资产组合，保持对象 ID、语义引用、单位及动作时间基准一致 |
| 初始状态与随机化 | `declaration()` 的 reset 范围、`_sample_box_reset` | sampler 使用明确的 seed、返回匹配当前 Artifact 的 ResetSample；不要手写来源摘要 |
| 奖励与成功 | `evaluate_task()` | 根据公开 state 和 semantics 返回 `TaskEvaluation`；区分任务成功与时间截断 |
| 动作与观测接线 | `selected_binding()` | 选择现有 action、observation 和 robot binding，assembly 负责 Controller 和来源身份；这些 binding 是当前内部扩展点 |
| Solution | Marker 没有 Solution；参考 Nut 的 `tasks/nut_assembly/solution.py` 及 `examples/tasks/nut_assembly.py` | task 拥有策略，调用方负责 `reset → act → env.step(action) → observe`，不要向 Env 增加任务专用专家入口 |

若任务不适用现有 Panda/table/box 组合，先核对现有组件能力和资产契约，不把 Marker 中固定的动作或物理参数当成通用接口。上述表格用于定位真实代码，不能证明任意新资产或 provider 可运行。

## 组合、重置、评价与 Solution

- **声明和资产**：task 选择稳定 UID、Scene/Agent/Object、语义与 timebase；assembly 编译资产和 references，provider 不从 task 读取私有 solver 状态。
- **reset**：task-owned sampler 定义随机化域和初态；显式 seed 应可复现。不同路线的默认 seed 语义不同，见 [episode reset](api/semantics/episode_reset.md)。
- **评价**：TaskDefinition 或示例评价函数区分 reward、success、failure 和指标。`terminated`、`truncated` 还由生命周期与 horizon 决定，不要把成功、Expert 完成和有效录制合并为一个布尔值。
- **Solution/Expert**：规范方向是由外部 Solution 消费 observation 并产生 action，再由调用方执行 `env.step(action)`。NutAssembly [示例](../../examples/tasks/nut_assembly.py)和[PickCube示例](../../examples/tasks/pick_cube.py)的普通CPU路线由调用方驱动 `act → step(action) → observe`。`step_with_solution()` 仍由 Env 调用 Solution，属于过渡接线；Nut 只接受带来源边界、Solution身份和控制请求的 `ExpertAction`。不同执行模式不能在同一 episode 混用。
- **验证**：先验证构造、reset、action/observation、reward/终止、close 和失败边界，再按实际 provider 与资产做有界运行。记录 `T` transitions 与 `T+1` boundaries，使用独立 reader；不要把注册、静态检查或单 slot 当作并行验证。

Empty、Pendulum 和 TwoWheel 的任务类使用统一 `SelectedReferenceEnv`；`BaseTaskEnv` 仅是同对象兼容导出。各任务仍提供自己的 scene、reset、动作、观测和评价。`make_parallel_env` 保留旧入口，统一路线并行适配留待 G06。阶段3–6的 renderer、controller 和 batch 设计尚非本次已实现能力。
