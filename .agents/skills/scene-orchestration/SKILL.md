在 GeoChora 仓库中使用时，先读 [GeoChora 单 Panda 资产场景交接](../geochora-task-harness/references/asset-scene-integration.md)。以该文档声明的任务、机器人与运行合同适配本技能；原项目的双臂、标准支架、head 相机和实例 `task.py` 约定仅适用于原项目配置。资产和材质制作方法仍按下文执行，GeoChora 的 reset、成功条件、控制、录制和运行准入由 TaskEnv 负责。


部署生成工具时使用仓库的[场景与资产 MCP 独立部署](../../../docs/module/task_env/v2.1.0/guides/asset-mcp-deployment.md)。本机资产服务为 `trellis2`、`ultrashape`、`trellis-texturing`；`experiment-batch` 仅管理独立会话。服务部署接受的真实 CUDA OOM 不代表该资产生成或验收通过。

# 场景生成与统筹

## 目标与职责

针对场景生成需求及适用的任务需求，统筹完整场景的设计、生成、域随机化、验收与交付，确保最终场景符合用户文字与图像要求，并满足约定的运行条件。具体资产与材质制作分别按同级的 `asset-creation`、`asset-material-creation` 处理。涉及机器人任务时，接收方另行提供 `embodied-task-creation` 或等效任务实现、运行时和机器人资产；本分发包保留必要的[具身集成约定](references/embodied-integration.md)，不包含这些外部实现。

各部分的具体检查过程由对应 skill 维护，本 skill 只说明如何汇总检查结果并判断完整场景是否满足交付要求。

Blender、生图与三维生成服务、Isaac Sim 由接收方环境提供。纯背景或单资产工作只执行适用步骤，不为满足任务格式虚构机器人、任务或评分。所有 `scripts/` 和 `references/` 路径相对于本 skill 目录；本次工作目录与 skill 安装目录分开。

## 工作流程

### 明确创建目标

场景还原度针对输入材料中原有的背景与物体。具身任务的被操作资产从接收方提供的资产库中选用，与额外加入的机器人、相机一并安排安装和操作空间，无需在原图中有对应物，也不要求其外观与原图一致。设计时优先利用现有空闲区域与支撑面；空间不足时，可清理或调整局部物体，并在设计确认时说明对还原度的影响，其余场景尽量保留。

用户提供的文字、图片、视频与平面图是场景生成依据。需求分为两类：

- **一比一还原需求**：仅用户输入图片为实拍的场景时可能为此项。要求创建出的场景在指定视角下呈现出与输入图片中的物体在风格、摆放方式上尽可能一致。
- **尺寸、风格、功能等其他需求**：对其他输入，遵循其中明确的布局、尺寸、风格与功能要求。

对还原型输入，保留其中可辨认的主要布局、物体组合、外观与空间关系；图片中无法确定的尺寸和遮挡部分按合理尺度补全。

域随机化限定于指定的对象、属性和范围；仅要求任务物体位置随机化时，不据此重新设计背景。已有背景和资产可直接复用。

以下双臂与相机规则用于兼容原项目的桌面任务。接收方须另行提供标准支架 USD 和 `installation.json`，其原项目资源名为 `standard_rig`；安装位姿、相机内参和修改限制见[双臂与相机安装约定](references/embodied-integration.md#双臂与相机安装约定)。新场景引用该资产并把实例放在 `robot_frame`；不重画钢架或另行摆放头部相机，实例只做整体平移和绕 Z 旋转。装配阶段可直接引用接收方共享资产；交付前把实际依赖复制到 `output/assets/` 并改为相对引用，`scene.usda` 不得依赖资产库路径。使用其他机器人配置时，在设计阶段明确目标运行时的安装与相机契约，不假定其遵循本双臂配置。
机器人根 prim 与相机 prim 的实际路径写入实例 `config.json` 的 `prims`：`robots.left`、`robots.right` 对应安装约定中的两臂，`cameras.head` 指向标准支架实例中的 `/Sensors/head` 路径（prim 名为 `head`），腕部相机按实际使用记为 `cameras.left_wrist`、`cameras.right_wrist`。场景装配时按安装约定摆放；运行入口按 `prims` 装配控制器并确定观测与录制相机。
头部相机以角色 `head` 记录，必须有且仅有一个。运行入口当前按 USD 中 prim 名为 `head` 的相机校验，所以 `cameras.head` 必须指向一个名为 `head` 的 `UsdGeom.Camera`；腕部相机只需是相机 prim。头部相机的位姿、焦距、分辨率和 aperture 由标准支架 USD 固定，不得在场景中另行覆盖；确需修改时先取得用户明确同意，并复验视野、遮挡和 `check_usd_static.py`。

### 制定方案并取得用户确认

制作前，在对话中向用户一并提交以下方案与图组：

- **需求理解**：哪些内容要求一比一还原，哪些有布局、尺寸、风格或功能要求；注明遮挡或无法确定、需要合理补全的部分。
- **场景与任务布局**：列出需要保留的关键区域、物体及其数量、空间关系与外观特征，作为还原清单。同时说明任务设备的位置与占地、必要的局部清理或调整，以及允许随机化的对象和范围；额外加入的任务设备单独标明。
- **设计图组**：使用生图工具制作以下图像，供用户确认外观和布置意向。
  - **空间视点图**：每个房间或局部空间 1～2 张，推荐最长边不超过 512 像素，从代表性观察位置以第一人称视角表现主要物体的布置、材料与氛围，并展示任务设备所处区域。
  - **资产示意图**：每个资产至少一张，推荐最长边不超过 768 像素；可动关节或多面细节较多时可增加至三张，后续资产制作可复用。还原型输入以原图为参考，保留目标物体的外观特征并补全遮挡部分，不直接裁剪原图作为资产参考图。

生图工具生成的示意图用于表达外观，不作为精确尺寸与位姿依据。设计方案与示意图均须遵循用户输入。

取得用户明确同意后，开始资产制作与场景装配。已确认的内容和随机化范围可沿用，不要求每个实例重新确认。

### 场景制作与装配

依据已确认方案完成背景和所需资产，具体制作按 `asset-creation`、`asset-material-creation` 执行。机器人、相机与任务设备按已确认布局装配，初态随机化、机制和判定绑定由接收方的 `embodied-task-creation` 或等效任务实现负责；缺失实现时记录未覆盖项，不声称任务已通过验证。

用三维空间布局 JSON 记录装配所用的位置、朝向等参数，作为具体装配依据；参数须符合已确认方案与用户输入，不以示意图推定精确位姿。

需要维护过程记录时，可使用[场景工作记录模板](references/scene_record.md)，放在本次工作目录的 `src/` 中；它不属于最终交付依赖。

生成过程中出现问题时，结合前后图像、实测结果和已尝试方法判断是否存在具体可行的新办法。首次发现不计入次数；问题已有缓解但仍未达标时重新计数。能够提出新办法时说明改动及预期改善后继续；对同一问题，连续三次修改后均未见实质改善时，停止围绕该问题反复返工，保留当前结果及未解决项，继续其他工作，并在交付时说明。

### 完整场景验收

以 Isaac Sim 加载的最终完整场景为验收对象，覆盖背景、资产、机器人、相机及具身任务。具体检查按对应 skill 执行，在此确认结果及其覆盖范围。

静态验收：
- **需求与布局**：对照已确认需求、还原清单与原始输入，逐项核对主要布局、物体组合、数量、空间关系、整体外观与照明。还原型输入附原图与相近视角的实际渲染并排图；检查差异是否属于已确认的局部调整或允许的随机化，不能仅以场景类别相同判定符合要求。明确尺寸用测量核对。额外加入的机器人、相机与任务设备不要求与原图对应。
- **支撑与空间**：检查家具及设备的支撑关系、机器人安装面、操作空间和通行区域，排除布局造成的悬空、非预期穿插与阻挡。
- **资产与材质验收**：确认 `asset-creation`、`asset-material-creation` 中适用的检查通过，证据覆盖最终场景中的实际安装与使用条件，包括组合后新增的物理和视觉问题。
- **具身任务验收（含任务时）**：核对[回合首帧条款](references/embodied-integration.md#回合首帧条款)，控制器、任务机制和判定器须在首个物理步之前接入，不得以加载后的沉降或预运行修补初态。确认外部任务实现的装配、初态、观测条件及机制与评分验证通过；结论注明是否覆盖机器人实际操作可达成性。
- **相机数量检查**：机器人任务中的每一个相机都应该对应真实存在的相机（原项目通常为一个 head 相机和两个腕部相机），不夹带观察用相机。纯场景的展示相机按已确认需求设置。
以上要求均满足后进行脚本验收：
- 在 Isaac Sim 的 Python 环境中执行本 skill 的 `scripts/check_usd_static.py <实例>/scene.usda --config <实例>/config.json`；`--config` 使用下述原项目双臂格式。无机器人背景省略 `--config`；其他机器人布局可通过 Python API 的 `roots` 参数显式传入冻结根路径，不能把未适配的配置套入此校验器。它会加载场景、保留原物理，测量 5 秒内物体移动是否超过阈值并报告具体问题。验收时机械臂会被冻结为静态几何，待操作物体必须由环境独立支撑，不得依赖夹持、与机械臂的固定连接或运动学跟随。脚本要求一个现有 PhysicsScene，不支持粒子、软体或 OmniGraph；这些情况须另行验证并记录覆盖范围。

合并同一轮发现的问题，修复后只复查受影响部分，同一次仿真或渲染的证据可用于多项检查。每个实例在交付时口头列明未通过和未覆盖项(若存在)。

## 输出目录结构

设交付的文件夹名称为 `output/`，其下仅允许下述结构定义的文件和目录。`scene.md` 仅记录未解决问题、未覆盖的验收项、影响使用的近似与限制，以及偏离已确认需求的情况；说明影响范围并引用必要验收证据，不写常规进度、制作过程或成功项流水账，不另建说明文档。资产依赖与验收证据分别归入 `assets/` 和各实例的 `checks/`，其余过程资料放在本次工作目录的 `src/` 中，可在交付后丢弃；正式交付及其说明、验收证据不得依赖或引用这些资料。

完整场景按批次交付，共享资产，每个域随机化实例独立存放初始场景及验收结果。含具身任务的实例还需任务实现与配置，使用下述结构；纯背景实例可省略 `task.py`、`config.json`，单资产交付仅使用 `assets/<asset_id>/` 及适用的验收证据。

```
output/
  scene.md                  # 未解决问题、验收缺项与使用限制
  assets/                   # 共享资产及纹理
  instances/                # 各域随机化实例
    variant_01/
      scene.usda            # 包含背景、机器人、相机与任务对象的静态初始场景
      config.json           # 本实例的 bindings、parameters、prims 与 instruction（必填）
      preview.png           # 本实例的实际渲染预览
      task.py               # 使用的机制与评分实现
      checks/               # 验收结论与证据
    variant_02/
      ...
    ...
```

### config.json定义
以下配置适用于原项目的双臂任务及配套 `--config` 校验器；其他运行时需要单独适配。每个 instance 文件夹下的 `config.json` 只包括如下四个 key：

- `bindings`：任务实现需要的语义对象到本实例实际 prim 路径的映射，值是路径或有序路径列表。名称、数量与顺序由该实例 `task.py` 的装配入口解释；任务代码不从对象名或布局推断路径。
- `parameters`：本实例冻结的抽样结果，例如随机种子、时间窗口与覆盖值。它必须足以在不重新采样的情况下复现这一回合；任务定义中的固定常量与阈值留在 `task.py`，不在此重复。
- `prims`：仅存储本实例中机器人根 prim 与相机 prim 的实际路径。`robots` 以 `left`、`right` 为键；`cameras` 至少含 `head`，腕部相机按实际使用记录为 `left_wrist`、`right_wrist`。运行入口据此装配控制器并确定观测相机角色。
- `instruction`：本实例的自然语言任务指令，原样提供给被测方法。只描述要完成的任务，不包含判定阈值、成功条件或评测侧信息。

运行入口按以下方式使用这些字段，交付时必须满足这些条件。它们对场景创建者视为黑盒约束，不需要了解控制器内部：

- `scene.usda` 文件名固定；`bindings` 与 `prims` 中的路径都必须在场景中存在。
- 每条机械臂一个根 prim（`robots.left`、`robots.right`），其子树内必须恰好有一个 `UsdPhysics.ArticulationRootAPI`，且该 articulation 是固定底座。安装关系必须写进 USD，不得依赖加载后的仿真或预运行建立。
- 一个实例的两条臂必须使用同一型号的机器人资产；关节名、限位与驱动参数沿用接收方机器人资产定义，不得在场景中改名或改驱动。
- `scripts/check_usd_static.py` 会按 `prims.robots` 冻结机器人，未记录的机器人不会被冻结。

不能写入 `config.json`的：几何尺寸、材质与摆放（都由 USD 表达）；机器人型号与驱动参数（由接收方机器人资产提供）；相机内参、位姿、分辨率与朝向（由 USD 表达）；代码中的默认值、阈值与固定常量（在 `task.py` 中）；评测倍率、样本数与模型配置（由运行入口决定）；验收结论与证据（在 `checks/` 中）。

提供了一个在mole具身任务下的config.json编写示例，见 [references/config.json](references/config.json)。

### task.py说明
实例 `task.py` 提供机制、判定和回合时间上限，须匹配接收方任务运行时的实际接口并满足零物理步要求。原项目当前以 `Task` 封装机制与判定，并由实例方法提供回合上限；不能把旧的模块级 `episode_horizon_s(parameters)` 当作通用接口。任务模板、运行入口与控制器不随这三个 skill 分发，接入边界见[任务运行时](references/embodied-integration.md#任务运行时)。
