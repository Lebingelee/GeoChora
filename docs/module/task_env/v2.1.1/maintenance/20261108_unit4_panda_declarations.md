# Panda source and controlled-subject boundary

The pinned Panda arm and hand source recipe remains owned by `task_env.assembly.panda_fixed_source`, including its two-source hash, namespace, fixed mount and tendon checks. `AssembledPandaAgent` declares the two robot components; task source composition preserves the task table and free cube and replaces the original robot representation. MuJoCo materialization checks the exact task and robot source closures, named entity and actuator ownership, the task free joint and the fixed attachment. A task-compatible mount is derived from the verified task hand frame and the pinned arm/hand source frames; it has its own plan identity and leaves the earlier candidate mount unchanged. The task end-effector site is copied from the verified task source into the declared hand component. Identical task and robot world elements are coalesced only after checking their values; conflicting declarations are rejected.

The normal selected PickCube configuration can explicitly request `robot: {uid: panda-v1}` or `robot: {uid: panda-arm-hand-v1}`. The latter currently admits only MuJoCo CPU with `task: {controller_profile: r1}` and state-only rendering; the separate component-runtime Controller route remains unsupported. The original omitted-robot configuration retains its prior route. Both explicit configurations compile the same Panda position Controller and controlled-subject contract; the integrated robot is a single entity and the assembled robot uses nested arm/hand ownership. Each position target must pass its bound subject, Controller, actuator mapping and current-episode interval checks before the session writes it. Controller input remains the existing eight-value world-pose/gripper action; the two finger joints share one tendon actuator. R1 position drives remain active and are not direct-effort commands.

The existing `pickcube-physical-candidate-v1` is the separately bounded 7+2 joint-effort route; it is not a newly added effort profile for either Robot selector. The new assembled route is not evidence of full task success, arbitrary attachment support, renderer capability, Isaac, GeoPhys physics or a cross-provider matrix. These results remain pending independent review and do not start a later work unit.
