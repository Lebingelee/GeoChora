# 诊断开发与核心代码边界规范

生效：2026-11-05。适用于环境、Controller、planner、provider／render adapter、recorder及其他核心类、方法和函数。本文是诊断开发的规范入口；TaskEnv的操作目录见[诊断说明](../../task_env/diagnostics/README.md)，v2.1.1的既存耦合处置见[维护规划](../module/task_env/v2.1.1/planning/pre-stage3-environment-refactor.md#diagnostic-policy-and-final-cleanup)。规范生效不代表旧代码已经全部符合。

## 一、依赖方向与基本职责

诊断程序引用核心模块，通过正常输入输出、公开state、现有Recorder和reader观察行为。核心模块不反向导入诊断／测试模块，不识别某个实验名、测试类、探针ID或临时工作路径来选择行为。诊断代码不参与正常产品路径的创建、推进或收尾。

核心保留产品所需的功能、契约检查与错误处理；任务策略归task／Solution，物理推进归runtime／provider，渲染归renderer，持久化与记录格式归recorder。诊断驱动可以组合这些已有对象，不能复制一套Env、Runtime、Controller或生命周期。

继承／重写是可用方式，外部驱动、组合与包装也适用。选择依据是既有接口和观察／干预需求，而非要求所有诊断都新增子类。任何方式都不能借诊断访问provider私有solver／renderer状态或绕过正式准入。

## 二、如何选择诊断实现

| 需求 | 实现位置与方式 | 必须保持的边界 |
| --- | --- | --- |
| 正常输入输出足够定位 | 在diagnostics或本次workspace中调用原对象，记录公开结果，做离线对照 | 默认首选；不修改被诊断类，不额外推进物理或render来假装同一边界 |
| 需要观察某次方法调用前后 | 外部包装／装饰方法或组合代理，调用原方法一次，采集允许公开的输入输出投影 | 返回值、异常、顺序和资源所有权保持；按buffer有效期复制需要保存的数据，不持有原生悬空引用 |
| 已有稳定扩展点需要受控干预 | 诊断目录中的子类，小范围重写相关方法，适用时调用super | 不重写整套reset／step／close，不复制基类大段实现；诊断类由诊断入口显式创建，不替换正常factory／UID注册 |
| 验证故障、错误反馈或组件替换 | 使用既有依赖注入接口、局部fake或测试fixture；确需monkeypatch时限定本测试／进程并恢复 | 不在核心增加`if is_test`、测试类识别或故障注入开关；替身结果只能证明对应契约 |
| 公开接口确实缺少必要信息 | 先用已有回执／记录／包装验证缺口；若信息也属于正式产品需求，则在正确owner中按正式API变更实现和评审 | 一次实验不能直接给核心添加probe或命名诊断callback；新增接口说明正常消费者、数据契约、开销与失效边界 |

普通函数的诊断同样可以在外部包装，不要求先把函数改成类。对照或干预若改变动作、控制律、反馈、时间或物理条件，要明确记录差异；诊断派生类的成功不能冒充未经修改的原实现成功，不伪造原类名或来源身份。

## 三、核心代码允许与禁止的分支

| 类别 | 规范 |
| --- | --- |
| 正常能力、类型、单位、来源、状态与生命周期判断 | 保留。backend路由、action校验、fault、stale／tamper、target/applied、有效性与close检查有产品语义；采用已声明的契约和现有owner |
| 产品正式日志、metrics或记录配置 | 可以存在；有明确消费者和默认开销，不改变物理、控制或准入语义，不伪装成实验特例 |
| 某任务的规划阶段、阈值、Solution具体实现判断 | 放task／Solution／specialization，不散布在通用Env、provider或renderer中 |
| 按实验名、测试类、caller、工作目录或诊断profile选择特殊行为 | 不新增到核心；实验差异在外部诊断驱动、子类或局部替换中显式组织 |
| 仅为诊断测试保留的核心私有兼容方法 | 测试应转向实际拥有该功能的模块。确有真实兼容消费者时明确登记，不能为了测试方便永久留在核心 |

不以“消除所有if-else”为目标。一个类／方法负责明确职责，状态、推进和资源有唯一owner；不同正式执行路线通过已有组件和分派接线，不在每个核心方法重复判断任务或实验名字。避免为缩短文件制造无独立职责的helper、mixin、Manager或一层层转发。

字段名包含`diagnostics`不自动意味着临时探针。正式控制请求、五样本反馈、故障和轨迹schema中的信息须按实际语义归类，不能仅改名或删掉负例。来源SHA、冻结资产和provider版本约束是否保留，也依据其正式契约判断，不统一当作诊断冗余。

## 四、诊断如何动工与结束

1. **先找参考闭环。** 明确待解决问题与预期结果，查找已成功的参考事例；核实其模型、控制、规划、初态和评价是否足以参考。没有参考时如实说明，不凭空列一长串猜测。
2. **确定实际owner和观察点。** 根据源码、生产调用者与已有测试定位被诊断类／方法，选择上表中的一种最小实现。仅列实际相关的条件和差异，不先进行全库审计。
3. **在外部准备最小对照。** 在诊断目录或独立workspace写驱动／子类／包装及短说明，通过控制变量逐项比较差异；分清被观测结果和人为干预。避免同时改变多项后单独归因。
4. **按变化验证。** 对实际改变的边界选择已有正负例；不为了每个小helper反复跑宽回归。保留运行来源、必要配置、命令、结果和局限即可，不为诊断另造资源／证据平台；既有运行安全约束继续适用。
5. **决定归宿。** 已确认的产品缺陷在正式owner修复，并保留针对性回归；临时采样、绘图和对照留在diagnostics／workspace。不能把某次实验的成功分支直接合进核心，不能用只返回静态结果的替身证明物理成功。

可复用入口和简短方法说明放`task_env/diagnostics/<topic>/`；仅供某轮使用的脚本、图表、原始数据放ignored `workspace/maintenance/<run>/`。测试沿用仓库已有位置，不新造测试目录体系。测试名称或所在目录不决定其是否为产品功能，依真实调用者判断。

每项诊断说明只需写：问题与参考、相关类／方法、对照条件、调用入口、结果及处置。明确期限或窗口时到时返包，不把未完的旁支变成自动续作。

## 五、代码评审与既存问题

后续开发／修复／重构包引用本文，评审至少回答：

- 正常路径是否新增了诊断参数、实验名／测试类分支或对diagnostics的依赖？
- 观察／干预能否通过外部驱动、包装、继承或现有注入完成？核心新增接口是否有独立的正式用途？
- 状态、推进和close是否仍由原owner唯一负责？任务策略、控制计算、渲染与记录是否放在正确模块？
- 结果证明的是原实现、受控干预还是fake契约？本次新增的诊断代码最终留在哪里？

现存耦合不要求现在逐个解耦，也不将其默认为合理设计。后续触及时记录“位置／实际用途／消费者／目标owner／保留或迁移理由”；能够在既定修改单元内安全归位的随该单元处理，暂不能处理的保持行为并登记，不新增更多诊断case沿用旧缺口。

v2.1.1在阶段3–6执行期间遵守新规则、登记已确认遗留；准备进入7a集成时集中分类与合理解耦，完成后再基于稳定源码进行后续代表性验证。保留正式能力、拒绝语义和历史原件，不把所有分支搬到另一个大类或另建诊断Runtime算作整改。
